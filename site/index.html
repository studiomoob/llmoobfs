Agent memory
as plain files.

An LLM agent that remembers across sessions usually keeps its memories as files and, beside them, a database that records what each one is. The application has to keep the two in step on every write. And who may see which memory is decided in application code, not by the operating system that already holds the files' permissions.

MoobFS is an experimental Linux kernel module that stacks over ext4, btrfs or XFS and moves those two jobs into the filesystem: the fields live on the files, the kernel indexes them, and a query answers only what the caller's file permissions allow.

Three parts.

Typed attributes on ordinary files

A memory is a file. Its fields are user.moob.* extended attributes, each with a type the kernel checks on write. Without the module, the directory is still a plain tree that grep, getfattr, git and rsync read.

An index in the kernel

The module indexes those attributes in RAM and updates the index when an attribute is written. There is no daemon. Nothing is scanned at mount: the first query on a directory builds its part of the index.

A query scoped by directory, authorized by file permissions

One ioctl on a directory answers up to four comparisons joined by AND, optionally ordered by one attribute. It returns only files that everyone allowed into that directory may read.

How to help.

The project has one maintainer and no outside human review yet.

What help is wanted ↗

The list is short and sorted by how much kernel knowledge each item takes:

  • If you know Linux filesystems or the VFS: review the credential model or the locking of the index.
  • If you build memory for agents: check whether your system fits one file per memory, fields as attributes and scopes as directories.
  • If you want to test: run the suite in a VM, try another kernel, or repeat a measurement on your hardware.
  • If you do not touch kernels: a few open issues need none.

Rules for changes are in the contribution guide ↗. A defect that crashes the kernel or that one user could use against another goes privately through SECURITY.md ↗.

How it works.

Writing a memory is an ordinary file write plus setxattr. Finding memories is one call on a directory.

Attributes are real user.moob.* xattrs on the lower filesystem, one type byte plus a payload (string, int64, double, bool, time, raw). The layer refuses invalid encodings on write and keeps an index in RAM, partitioned by permission domain: by default, each top-level directory of the mount. QUERY2 on a domain directory takes up to four predicates joined by AND and answers from that domain's partition after one permission check on the directory. The older mount-wide QUERY checks each result and is for administrators. GET_INFO reports the index state and the lower filesystem's capabilities.

Storage and context have distinct roles

The filesystem stores, validates and queries. The agent application selects what is relevant and assembles the context sent to the LLM. There is no semantic or vector search in the kernel and no daemon. MoobFS does not assemble prompts or extend a model's context window; memory frameworks are potential clients, not competitors.

Nothing is trapped: unmount the layer and the lower directory is a plain tree that grep, getfattr, git and rsync read without the module.

What was measured.

The report ↗ that answers the four questions of the benchmark plan is a pilot-grade report.

Every campaign is pilot-grade: one data-set seed, three repetitions at most, often one run, and a run-to-run noise of about 20 to 25 % on values of tens of microseconds. Numbers from different hosts are not compared with each other. The index code changed after most of these measurements and they were not repeated.

What the layer adds per operation, on the current module (10 000 memories, medians, bare lower against the layer): a read by path goes from 8.5 to 11.0 µs on ext4; setting one attribute from 8.9 to 21.7 µs; creating a memory durably is unchanged within noise, because the device flushes take 12 to 14 ms.

What a side database costs at write time, which this project had assumed and never measured: almost nothing. Publishing a memory durably takes 6.6 to 8.5 ms with the file alone and 6.6 to 8.7 ms with a row added to a SQLite database in its usual mode; through the layer, with eight attributes, 7.0 to 9.8 ms. The layer does not make writes cheaper. What it removes is the second copy of the fields, which can disagree with the files after a crash.

Where the layer wins

  • Selective queries inside one directory. On a synthetic set of 60 000 memories, 1.1 to 6 times faster than SQLite with composite indexes on the five shapes measured; the low end is a tie at SQLite's best case.
  • Three of a real client's six query shapes are faster, by 5 to 6.5 times and 1.6 to 3.8 times on the two clearest, with equal answers in every check.
  • That client runs unchanged on the layer. Its 1 147 tests pass and its retrieval results are identical, after a layer defect it exposed was fixed.

Where it loses, ties or costs

  • Long ordered traversal. 0.71 to 0.51 of SQLite's speed, worse as the answer grows. Two other shapes of the same client are ties.
  • The first interface (the mount-wide QUERY) is slower than SQLite on every shape that returns results: 18 times slower at 60 000 memories in one campaign.
  • Fields of the results. A query returns paths. Reading all attributes of a result costs about 16 µs per file, against about 0.9 µs per result for the query; SQL returns columns in the same call, and no comparison here counts this.
  • Mount time. 0.7 s warm and 18.5 to 19.3 s cold for 60 000 files on a SATA SSD; 126 s cold on a cloud disk.
  • Memory. About 0.5 to 0.6 KiB of kernel memory per file that cannot be paged out, by the index's own accounting, which undercounts.
  • The real client's writes were about 10 % slower in one run, and a page it writes is queryable about 11 ms later: a separate process copies its fields into attributes. The client itself never called the query; a test tool did.
  • Reflink and dedupe work through the layer, but the saving is the lower filesystem's and is small for small files: 6.7 % on btrfs and 13.6 % on XFS where 15 % of the files are copies, none on ext4.

Not measured: CPU and memory per query, concurrency, a second client's latency, repetitions with confidence intervals. Raw results and scripts ↗

Try it in a VM.

One command builds the tools and the modules and boots a disposable QEMU VM with the pinned Linux kernel. Docker supplies the toolchain; the host kernel stays outside the experiment. Never load the modules on a machine you care about.

Native test instructions →
git clone https://github.com/studiomoob/llmoobfs.git
cd llmoobfs
make vm-test

# only the demonstration at the top of this page
MOOB_ONLY=demo make vm-test
grep '^DEMO| ' build/vm/console.log

Requires Docker. Runs Debian kernel 6.12.111+deb13-amd64. A passing full run ends with MOOBFS_VM_PASS, LAYER_LOWER_PASS for ext4, btrfs and xfs, MOOBFS_ACCEPTANCE_PASS and MOOBFS_LAYER_PASS; a MOOB_ONLY run ends with MOOBFS_ONLY_PASS, which is not a complete run. Logs and environment details are written to build/vm/.

Comparison and when not to use MoobFS ↗ · Adoption risks ↗

Facts verified in the repository as of 2026-10-18:

  • Tested on one kernel series in a VM (Debian 6.12.111 in QEMU; upstream 6.12.112 under KASAN/UBSAN/lockdep), x86-64, over ext4, btrfs and XFS only; under KASAN, UBSAN and lockdep on every pull request that touches the module, with fault injection, fstests' quick group and syzkaller.
  • The attribute index lives only in RAM, cannot be paged out, is bounded by a budget (128 MiB by default) and is built per domain by the first query on it; built domains are released under memory pressure or to stay within the budget.
  • Mounting requires CAP_SYS_ADMIN in the initial user namespace; user-namespace and idmapped mounts are refused, and so is an idmapped mount as lower=.
  • The interface (UAPI v1 and v2) may change, with no compatibility promise. The tags are source snapshots, without binaries, packaging or support.
  • Measurements are pilot-grade and are not a general speed claim.
  • No outside human review. Two source reviews by AI assistants and the project's own tests found and fixed kernel-side defects, security ones among them (findings F1 to F12 of ADR-0011); syzkaller ran for three six-hour rounds and fstests as its quick group only. Every tag so far carries defects fixed later: build from main.
  • Reflink, deduplication and durability come from the lower filesystem, not from MoobFS.

What the tests do show, within those limits: kernel answers are compared with a user-space oracle; two users on the same mount do not see each other's memories; git and WAL-mode SQLite run unchanged on the mount; power-loss replay keeps every synced memory.

Planned without dates.

  1. DONE · M1

    Native shared reads

    Read-only image, two inodes sharing one payload, 15 malformed images rejected; frozen, runs as a regression.

  2. DONE · M2 2a–2e

    Stacked layer, typed attributes, index, QUERY

    Pass-through over ext4, btrfs and XFS with fsx; typed user.moob.* validated in the kernel; in-memory index; QUERY and GET_INFO equal to the oracle; acceptance with git, SQLite WAL, dm-log-writes and dm-flakey.

  3. DONE · KASAN

    Instrumented kernel harness

    Upstream 6.12.112 with KASAN, UBSAN and lockdep runs the same suite on every pull request that touches the module (required before merge) and weekly.

  4. DONE · M3 3b

    POSIX authorization in QUERY

    Each result resolved with the caller's credentials; two users, ACLs, remount, idmapped and user-namespace mounts refused, race test; passed in the VM and under KASAN.

  5. DONE · QUERY2

    Query per directory

    Issued on a domain directory, index partitioned by domain, ordering and cursor, batches; answers equal to the oracle on ext4, btrfs and XFS.

  6. DONE · ADR-0012

    Index on demand

    Each domain's part of the index is built by its first query and released under memory pressure or over its budget; nothing is scanned at mount.

  7. IN PROGRESS · STABILIZATION

    Hardening what exists

    Fault injection, fstests, syzkaller, KCSAN and SELinux runs; twelve findings of the threat model recorded, all but two fixed; no new features until this round closes.

  8. IN PROGRESS · M4

    Measurement report

    Pilot-grade campaigns against SQLite and one real client are recorded, including where the layer loses; latency per operation on the current module is pending.

  9. DEPENDS ON VALIDATION

    Persistence, attribute values with results, release

    Index persistence, returning attribute values with query results (specified in ADR-0014), a change cursor and any public release wait for the stabilization round, the measurements and the security roadmap.
