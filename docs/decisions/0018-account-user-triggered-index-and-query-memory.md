# ADR-0018 — Account user-triggered index and query memory to memcg

Date: 2026-10-22. Status: **accepted; integrated by PR 129 on 2026-10-23**.
Estimated effort: M (one to three days).

## Context

ADR-0012 bounds the in-memory index by a per-mount budget and releases built
domains under pressure. ADR-0011 records fair sharing of that budget as future
S9 work. Neither makes the kernel memory generated by an unprivileged query
visible to a memory cgroup. Issue 116 also notes that `QUERY2` may retain a
result buffer of up to 4096 × 272 bytes for the lifetime of an open file.
This decision supersedes only ADR-0012's assumption that index memory is not
memcg-charged; its on-demand build and reclaim design remain in force.
Journal 0139 measured roughly doubled query latency when that buffer was
allocated and freed on every call; the reuse is intentional.

Linux 6.12.112's `Documentation/core-api/memory-allocation.rst` recommends
`__GFP_ACCOUNT` for untrusted userspace-triggered kernel allocations and
provides `GFP_KERNEL_ACCOUNT`. Its `mm/util.c` passes that flag through the
kvmalloc fallback, and `mm/vmalloc.c` records vmalloc pages when the flag is
present. See `docs/references.md` and journal 0180 for the exact sources and
bounded guest measurements.

## Decision

Pass `GFP_KERNEL_ACCOUNT` for allocations made by the index, scans and query
paths, including xarray nodes, result candidates and both the retained and
concurrent-fallback result buffers. Keep the existing per-mount budget and
per-open buffer reuse. The charge belongs to the current task's memcg when
each allocation occurs; an index can consequently contain objects charged
to different cgroups. Closing a query descriptor frees its retained buffer;
releasing a domain or unmounting frees its corresponding index charges.

This changes resource accounting and possible cgroup-limit outcomes, not
`QUERY2`'s UAPI, attribute encoding, image format or on-disk data. On kernels
without `CONFIG_MEMCG`, the account flag does not provide a cgroup limit; the
per-mount budget and per-call result limit still apply. Memcg accounting is
not S9 fair sharing and does not assign cost by file owner or transfer a
charge if a descriptor is passed to another cgroup.

## Alternatives

- Keep plain `GFP_KERNEL` and rely on `index_budget`: leaves the per-open
  buffer outside that budget and invisible to memcg; rejected for issue 116.
- Free the result buffer after each query: journal 0139 measured a substantial
  latency regression for that approach. Keep reuse and make the cost visible.
- Charge every index record to the file owner's cgroup or divide the mount
  budget by uid: ownership and charge migration are different policies that
  require S9 design and tests; do not imply them here.

## Validation and limits

The targeted Debian 6.12.111 VM test in journal 0180 passed for the retained
buffer and the built index, with separate negative controls for each. After
PR 127 was integrated, the full native-KVM suite passed on ext4, btrfs and
XFS, including `MEMCG_ACCOUNT_PASS`, index release and the over-budget race.
The full integrated KASAN/UBSAN/lockdep run also passed. The project's pinned
KASAN 6.12.112 kernel lacks `CONFIG_MEMCG`, so that run detects memory-safety
regressions but cannot prove cgroup charging. The Debian VM has
`CONFIG_MEMCG=y` and executed the accounting test rather than silently
skipping it.

The accounting flags preserve the existing allocation sizes and lifetimes;
they add cgroup charging and may cause allocation failure at a cgroup limit.
No controlled before/after performance comparison was run, so the overhead
is unquantified. The first publication, PR 128, failed its commit sign-off
gate; [PR 129](https://github.com/studiomoob/llmoobfs/pull/129) is its
replacement without a history rewrite. Acceptance of the design is not a
pull-request CI or merge verdict. Issue 116 stays open until integration.
